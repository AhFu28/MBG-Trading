fix(api): data endpoint served HTML with HTTP 200 - real cause of every desk erroring

JENDRAL ARIB: "kenapa masih sama bentukan futures dan forexnya masih error2 aja"

It was never futures. It was never forex. It was EVERY desk, and the cause was
one endpoint lying about its own health:

    GET /api/data
    -> HTTP 200
    -> Content-Type: text/html
    -> 1 KB
    -> body: <!doctype html><html lang="en">...

TWO FAULTS COMPOUNDED

1) The engine stopped writing frontend/public/data for a good security reason:
   supabase_client.py used to mirror every VIP payload (trade plans, arena
   state, macro telemetry) into a publicly downloadable static file that needed
   no authentication to fetch. Removing that write was CORRECT.
   But the endpoint kept fetching /data/latest_cockpit_bundle.json. Nothing
   updated the fetch path, so production asked for a file that had been
   deliberately deleted.

2) Cloudflare Pages answers a MISSING path with index.html and HTTP 200. So
   the `if (!dataResp.ok)` guard never fired, and the HTML was forwarded to the
   client as if it were market data. The cockpit then crashed on JSON.parse
   while the server reported perfect health.

WHY THIS MATTERED MORE THAN IT LOOKS
An API that returns 200 + HTML for a data request is worse than one that fails.
The client cannot tell the difference, and neither can monitoring. It also sent
us chasing phantom bugs in futures and forex code that was perfectly fine.

FIXES
  - parseBundle() rejects HTML by content type AND by inspecting the body, so a
    proxy that mislabels the type cannot slip through.
  - A missing or invalid bundle now returns 503 with a hint, and is marked
    X-Data-Source: invalid so it is visible in logs.
  - Error responses are Cache-Control: no-store. A cached 503 would keep the
    cockpit broken long after the fix shipped.
  - Added an optional edge KV binding (MBG_BUNDLE) so the bundle can live at the
    edge WITHOUT being a public static file - this preserves the security fix
    while restoring data flow.
  - scripts/push_bundle_to_edge.py pushes to Cloudflare KV or a self-hosted
    endpoint, and refuses to invent a destination when none is configured.

TESTS: 19 new in dataEndpoint.test.js. The central one asserts the endpoint does
NOT return 200 when Cloudflare serves index.html, and that no HTML body is ever
forwarded to a client. Also covers the KV binding, Supabase preference, and
cache safety on errors. 225 frontend tests pass (up from 206). Build clean.

STILL REQUIRED TO FULLY RESTORE LIVE DATA (owner action):
Set SUPABASE_URL + SUPABASE_KEY in Cloudflare, or create a KV namespace and bind
it as MBG_BUNDLE. Until then the endpoint correctly reports 503 instead of
serving garbage - the cockpit will show an honest error rather than crashing on
HTML.
